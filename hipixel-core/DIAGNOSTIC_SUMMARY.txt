================================================================================
                         DESIGN IMPLICATIONS
================================================================================

1. LIBRARY vs CLI DUALITY
   • Core modules (pipeline, backends, filters) designed as silent libraries
   • Only CLI (cli.py) provides user-facing output
   • Enables library reuse but sacrifices debuggability

2. RICH INTEGRATION
   • Rich is already a dependency (13.7.0+)
   • Already used: Console, Progress, Table, markup
   • NOT used: logging.Handler, File rotation
   • Recommendation: Use Rich for both console + file output

3. THREADING ARCHITECTURE
   • 3 daemon threads: decode → process → encode
   • Exceptions from all threads collected in list
   • Only first exception propagated (potential data loss)
   • No per-thread logging means silent failures in I/O threads

4. TILE-BASED PROCESSING
   • Real-ESRGAN computes tile size based on VRAM (lines 116-130)
   • Tile calculation is completely silent
   • No logging of: tile count, tile size, overlap, tiling strategy
   • Essential for debugging memory issues

5. PLATFORM-SPECIFIC BACKENDS
   • CoreML: Silent ONNX→MLPackage conversion (could take seconds)
   • CUDA: Silent pynvml VRAM probes (could fail silently)
   • CPU: Always available, no special handling
   • Each backend needs targeted logging

================================================================================
                             CONCLUSION
================================================================================

The hipixel-core codebase currently has NO logging system. All output is
console-only, confined to the CLI layer, and core modules are intentionally
silent. This design is good for library reusability but bad for debugging,
troubleshooting, and operational visibility.

The logging architecture must be designed from scratch to cover:
  1. Module-level logging with appropriate verbosity
  2. CLI-controlled output (--verbose, --quiet, --log-file)
  3. Exception context enrichment
  4. Per-filter and per-thread diagnostics
  5. VRAM tracking and tile-based processing visibility

Implementation should follow Python logging conventions, leverage Rich for
console formatting, and maintain backward compatibility with existing output.
